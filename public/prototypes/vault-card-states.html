Unified vault card — kanban view draft · prototype only · one card component, every state

The kanban currently uses three different card components: app-grooming-card, app-execution-card, and an inline manual card. This prototype proposes a single app-vault-card driven by a discriminated CardContext union. Two structural changes from the current design: owner and project are always-on (rendered on every card via strengthened pills) and epic cards roll up child state via a per-child status strip so progress is visible without a click-in.

06 Epic + task chips — identity in the pill, hierarchy on the card

A chip is the entity's identity card — used in mentions, lists, threads, anywhere the item is referenced away from the kanban. The kanban card itself shows hierarchy and state on top. The principle: chip = identity + class; card = relationships + state. Don't try to encode hierarchy into the chip — it can't render reliably at the sizes a chip lives in.

Vault-item chips · three kinds, one shell

What the colour does here: the hermes pink wash on the epic chip, parent-link bars, and project pills all derive from the same project token. Drag-eye from the epic down to its children and the colour stays continuous. Switch to a different epic in a different project, and the wash shifts in lockstep — the operator knows project-context without reading.

Four orthogonal axes — no colour collisions

  1. Mid-tone muted = project identity (project pill solid, epic 45% wash, parent-link bar, all chip stripes, card border-left). Strong enough to scan, off-axis enough not to compete with primaries.
  2. Primary = state (P0 red, running blue, completed green, failed red, draft yellow). Loud, demands attention, never confused with identity.
  3. Monochrome = ownership (actor avatars, source attribution, owner names). Actors carry no colour at all — frees the whole primary palette for state.
  4. Border style = creator class (solid = agent-made, dashed = human-made). Applies to both epic chips AND actor avatars — one rule, not two. Free signal, no colour cost.

Final design rules (the things to lock down before code):
  • Project = mid-tone muted colour. Solid pill in identity strip. 45% wash on epic chips. 3px stripe on every other chip + card border-left. Inline name /projectname in card header next to seq.
  • Actor = monochrome only. Outlined ring (solid = agent, dashed = human). Full name in identity strip; initial-only when connected/secondary. No actor colour anywhere on the card.
  • State = primary colours only. Priority badges, dispatch status, callouts. Reserved palette so they never get confused with identity chrome.
  • Solid vs dashed applies the same way to both epic chips and actor avatars: solid = agent-made, dashed = human-made. One rule.
type CardContext =
  | { kind: 'grooming'; item: VaultItem; openQuestion: ThreadMessage | null;
      project: ProjectRef | null; owner: ActorRef;
      childRollup: ChildStatus[] | null;          // null when not epic
      daysInColumn: number; lastActivityAt: string | null;
      source: SourceAttribution | null; }
  | { kind: 'dispatch'; entry: DispatchQueueEntry; item: VaultItem | null;
      skillDisplayName: string | null;
      project: ProjectRef | null; owner: ActorRef; }
  | { kind: 'manual';   item: VaultItem;
      project: ProjectRef | null; owner: ActorRef;
      source: SourceAttribution | null; };

interface ChildStatus {
  seq: number;
  state: 'grooming' | 'ready' | 'running' | 'completed' | 'failed';
}
Owner is non-nullable in CardContext. Today VaultItem.assigned_to can be null; in practice every actionable item ends up owned by someone before it leaves grooming. The board resolves owner with a fallback (e.g. @marvin for unassigned) so the card never has to render an empty owner slot — and the operator never has to wonder.
